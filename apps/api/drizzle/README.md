# Migrations

Generated by `drizzle-kit` from `src/shared/persistence/schema.ts`, applied as
the schema owner, and reviewed by hand before either happens.

```bash
pnpm db:generate   # write NNNN_name.sql + meta/NNNN_snapshot.json from the schema
# read the SQL, then write notes/NNNN_name.md
pnpm db:check      # two branches that both generated a migration collide here
pnpm db:migrate    # apply, as MIGRATION_DATABASE_URL (role `app`, not the runtime role)
```

`pnpm db:check` runs inside `pnpm check`, so a journal that disagrees with the
directory fails before anything reaches a database.

## Why every migration has a note

`drizzle-kit generate` writes SQL that matches the schema and has no opinion
about locks. `0004_millisecond_instants.sql` is twenty `ALTER COLUMN … SET DATA
TYPE` statements — a rewrite of every row in five tables under `ACCESS
EXCLUSIVE`. It was harmless because the tables were empty, and nothing anywhere
said so. The next migration of that shape will look identical.

So each one carries `notes/<tag>.md`, and
`tools/migrations/__tests__/migrations.spec.ts` compares the note against the
SQL. It fails when the note misses a locking statement the file contains, and
when it lists one the file does not — a note copied forward from the last
migration is worse than none, because it reads as though somebody looked.

Start from `notes/TEMPLATE.md`. It carries the four rewrites that turn a
blocking statement into a survivable one.

## The rules the test enforces

| Rule                                                 | Why                                                                           |
| ---------------------------------------------------- | ----------------------------------------------------------------------------- |
| Every `.sql` has a note, and every note has a `.sql` | Otherwise the habit lasts until the week it matters                           |
| The `## Locks` list matches the SQL exactly          | Both directions, so a stale note fails                                        |
| `## Rollback` says something                         | "It cannot be undone, and this is what is lost" is an answer; silence is not  |
| No `ADD COLUMN … NOT NULL` without `DEFAULT`         | Rewrites the table, then fails on it if it has rows. No note excuses this one |
| The directory matches `meta/_journal.json`           | A file added or removed by hand                                               |

A statement on a table the same migration created is not counted: nothing else
can be reading a table that did not exist four statements ago, and counting
those would make the initial schema the riskiest file here and teach everyone
to skim the list.

## Expand → migrate → contract

Anything that is not additive is more than one deploy: add the new shape
nullable, write both, backfill in batches, switch the readers, then drop the
old shape and tighten the constraint. Every migration in this directory today
is additive, which means the discipline has not been exercised yet — the
template is what makes the first time not require inventing it.

## What never happens here

- `drizzle-kit push` outside a personal machine. It skips the history, and two
  environments then differ by whatever somebody pushed.
- Editing an applied migration. `drizzle-orm` hashes the file and would treat
  the edit as a migration nobody has run. Notes live in `notes/` for this
  reason: they can be corrected without touching what was applied.
